## State of the art architecture

For this category, “state of the art” is not one model or one framework. It is a composition of **entity graph + event bus + hybrid retrieval + specialist tools + auditable orchestration**. Microsoft’s GraphRAG work is especially relevant because it is explicitly designed for private narrative datasets where baseline semantic search “struggles to connect the dots,” and it adds graph extraction, community hierarchy, global search, local search, and DRIFT search for questions that require either entity-centric reasoning or corpus-level synthesis. That maps unusually well to your domain, where an answer often depends on linking customer history, prior tickets, deployment changes, telemetry anomalies, code references, and operational entities rather than retrieving one FAQ chunk. citeturn26view0turn26view1turn26view2

The retrieval layer should therefore be **hybrid by default**. Plain semantic search is useful, but hybrid search combines keyword precision with vector retrieval and can merge both through reciprocal rank fusion; agentic retrieval extends classic RAG by decomposing complex inputs into multiple focused subqueries; and indexes can keep citation-quality metadata attached so the system can explain where evidence came from. For your niche, that likely means at least four retrieval modes in one plane: exact keyword retrieval for IDs, versions, error codes, and ticket fields; semantic retrieval for runbooks and historical text; graph/entity retrieval for cross-account or cross-incident reasoning; and time-bounded telemetry/log retrieval for incident windows. entity["company","OpenAI","ai company"]’s Retrieval guide, Microsoft’s Azure hybrid-search guidance, and Microsoft Foundry’s agentic-RAG guidance all point in that direction. citeturn25view0turn11view6turn25view1

For orchestration, the best current guidance is more conservative than much of the agent hype. entity["company","Anthropic","ai company"] argues that the most successful production systems use simple, composable patterns rather than complex frameworks, and it distinguishes structured workflows from more autonomous agents. OpenAI’s practical guide similarly recommends maximizing a single agent’s capabilities first, using prompt templates and clear tools, and only moving to multi-agent patterns when tool overload or specialization justifies it. The implication for your design is important: keep a **single control-plane manager** responsible for overall state, policy, and synthesis, and expose your specialist investigators as tools or tool-like subagents whose boundaries are clear, typed, and separately testable. That preserves the modularity you want without paying unnecessary orchestration tax. citeturn17view2turn17view3turn17view0turn17view1

A real control plane also needs first-class **agent observability**. ## Reliability, governance, and security

Classic SRE is not obsolete here; it is the substrate. Google’s SRE guidance still gives the right instincts: alerts should be timely, symptom-based, and actionable; toil is the manual, repetitive, automatable, reactive work that should be pushed down by engineering; postmortems should be blameless and feed corrective actions back into the backlog; and error budgets exist to provide an objective metric for balancing reliability and change. What changes in your space is that these principles must now operate across support, customer communications, fleet operations, and AI-driven workflows, not just server infrastructure. citeturn22view1turn22view0turn22view2turn22view3turn22view4turn24view4

The right autonomy model is **progressive, not absolute**. Datadog is already emphasizing visible agent reasoning and human-in-the-loop response actions; Dynatrace talks about a journey from automated root cause and corrective actions toward autonomous operations “with your team at the center”; Pylon explicitly recommends pilot and shadow-mode testing before direct customer interaction; and OpenAI’s guardrails guidance is unambiguous that sensitive side effects such as edits, cancellations, shell commands, or sensitive MCP actions should pause for approval or be surrounded by tool-level validation. In your domain that means the assistant/copilot/executor boundary should be policy-driven by issue type, severity, customer sensitivity, and action class, not by generic model confidence alone. citeturn21view3turn13view8turn14view1turn16view2

Security and permissions are not an afterthought once MCP and live tools enter the picture. The official MCP security guidance explicitly calls out confused-deputy problems, token-passthrough risk, SSRF, session hijacking, local server compromise, and scope minimization, while the MCP roadmap is pushing toward finer-grained least-privilege scopes and stronger credential handling. ServiceNow’s latest AI Control Tower messaging is notable for the same reason: runtime observability into agent decisions, least-privilege enforcement, and the ability to shut down an out-of-bounds agent in real time. For your architecture, “guardrails” should therefore include hardcoded permission envelopes, per-tool approval policies, environment scoping, and kill switches, not just soft prompt instructions. entity["organization","NIST","us standards institute"] also matters here because its AI RMF is now being extended with a critical-infrastructure profile, which is directionally aligned with your high-stakes industrial setting. citeturn16view0turn17view8turn16view1turn28view4turn28view5turn11view11

## Prototype scope that maximizes signal

For a recruiter-facing artifact, the prototype should prove one thing above all else: **you understand operational AI as a real system under real constraints**. The ideal story is not “I built bots.” It is “I built a governed control plane that can investigate, explain, and safely act across messy technical operations.” That framing is much closer to where Datadog, PagerDuty, Atlassian, ServiceNow, and Formant are all pushing the market, but your version can be more compelling because it is grounded in physical systems, account context, and high-complexity support. citeturn21view3turn11view18turn28view0turn28view3turn11view14

The highest-signal prototype would center on a **single entity-centric investigation flow**. A support ticket, anomaly alert, or blocked-robot event enters the system; the control plane resolves the relevant account, site, fleet, robot, software revision, and severity context; the investigator retrieves evidence across docs, prior tickets, code, telemetry, and logs; a specialist diagnostics agent is optionally called for a narrow task; the system assembles a traceable triage packet with hypotheses, evidence, and recommended next actions; and the final layer generates two bounded outputs: an internal operator briefing and a customer-safe draft response. That design directly borrows the best ideas currently visible in Pylon’s codebase-aware and MCP-aware issue assistance, Datadog’s hypothesis-driven investigation and Agent Trace, Foxglove’s rosbag/log debugging, Roboto’s automated analysis over complex robot logs, and Formant’s emphasis on investigation plus triage packets. citeturn23view5turn23view6turn21view4turn21view3turn30view1turn30view0turn11view14

What you should **not** build, at least for this artifact, is a full omnichannel support product, a full observability platform, or a fully autonomous remediation engine. Anthropic and OpenAI’s guidance both argue for simple, composable patterns and warn against premature multi-agent complexity. So the right realism level is selective: real local services, real typed tools, real traces, real dashboards, and realistic synthetic data, but narrow enough that the evaluator can understand the entire system in one sitting. The strongest demonstration is depth of reasoning and governance, not breadth of surface area. citeturn17view2turn17view0

## Roadmap from artifact to platform

**Phase one** should produce a tight credibility artifact: one end-to-end investigation flow; a small but realistic entity model; a hybrid retrieval layer over synthetic tickets, docs, telemetry snapshots, and code snippets; one or two specialist agents; policy gates for sensitive actions; and a visible trace that shows prompts, tools, evidence, hypotheses, and final recommendations. Include a Grafana-style or equivalent operational view, but keep the UI secondary to the investigation trace and evidence packet. Datadog’s Agent Trace, OpenAI’s tracing guidance, and Langfuse-style observation structure are the best models for what “convincing” looks like here. citeturn21view3turn17view7turn23view4

**Phase two** should make the system feel like a real operational substrate rather than a demo: richer connectors, time-bounded telemetry queries, a customer/account memory layer, severity-specific policies, cost and latency instrumentation, error-budget or reliability state, and the ability to turn one investigation into durable knowledge. This is where GraphRAG or a graph-adjacent entity layer becomes more valuable, because the prototype starts to answer not only “what happened here?” but also “where else have we seen this pattern?” and “which accounts or fleet segments share the same failure mode?” That is also the phase where continuous evaluation and shadow-mode operation become essential. citeturn26view1turn14view1turn18view5

**Phase three** is the founder-grade roadmap, and it is worth articulating even if you never build it. The roadmap should show how the prototype could evolve into a broader system that can discover assets, observe runtime behavior, govern actions, measure ROI and cost, and safely orchestrate bounded automations. ServiceNow’s “sense, decide, act, and secure” framing is useful here, as is the way Pylon, Atlassian, and New Relic tie operational context back to customer outcomes or business observability. If you include that roadmap in your README or architecture note, it signals ambition without forcing you to build the whole thing now. citeturn28view3turn28view5turn28view2turn29view1
